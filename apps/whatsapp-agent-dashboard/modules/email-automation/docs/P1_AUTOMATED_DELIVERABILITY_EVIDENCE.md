# Email P1 — Automated Deliverability Evidence

## Purpose

P1 replaces manually asserted deliverability environment values with durable, sender-domain evidence generated by the application itself. It does **not** enable customer delivery. `DRY_RUN` and `EMAIL_EXTERNAL_WRITES_ENABLED=false` remain the production posture until later rollout gates are separately approved.

## Source of truth

Each connected Email channel persists an `emailDeliverability` capability snapshot keyed by sender domain. The snapshot is refreshed by the Email scheduler and can also be force-refreshed by an Email manager.

Scaled automation (`LIMITED_COHORT` or `LIVE`) loads the snapshot for the **resolved sender after provider routing/failover**. A different failover sender therefore requires its own qualified evidence.

Legacy values such as `EMAIL_DELIVERABILITY_SPF_ALIGNED` and manually supplied bounce/complaint rates are not accepted as runtime evidence.

## Automated domain authentication

For every active verified sender domain:

- SPF TXT is resolved from the sender domain.
- The SPF record must be singular and must authorize the configured provider family.
- Gmail qualification expects `_spf.google.com`.
- Microsoft 365 qualification expects `spf.protection.outlook.com`.
- DKIM is resolved using provider defaults (`google` for Gmail; `selector1` and `selector2` for Microsoft 365) or explicit provider selector overrides.
- DKIM TXT or CNAME evidence must exist for every required selector.
- DMARC TXT is resolved from `_dmarc.<domain>` and must contain a valid `p=none`, `p=quarantine`, or `p=reject` policy.
- Transient DNS resolver failures remain `unknown`; missing or invalid records remain unqualified.

## Automated reputation evidence

The service calculates a rolling hard-bounce rate from persisted Email data:

- denominator: external Email messages sent in the configured rolling window;
- numerator: unique messages with `BOUNCED` analytics events whose persisted metadata classifies the bounce as `HARD`.

Default reputation window: 168 hours (7 days).

Current Gmail/Microsoft connections do not provide an authoritative complaint/spam telemetry feed through the existing OAuth/provider adapters. P1 therefore records complaint events when present but marks the complaint source as `UNAVAILABLE`. A zero complaint count is **not** treated as authoritative zero complaint rate.

This intentionally means scaled delivery remains fail-closed until a separately reviewed complaint telemetry source is connected.

## Freshness and safety gates

Default evidence refresh cadence: 60 minutes.
Default maximum evidence age for scaled delivery: 1440 minutes (24 hours).

Scaled delivery blocks when any of the following is true:

- evidence is missing, invalid, future-dated, or stale;
- SPF provider authorization is not qualified;
- DKIM sender-domain authentication is not qualified;
- DMARC policy is not qualified;
- hard-bounce telemetry is missing or reaches/exceeds 5%;
- authoritative complaint telemetry is not qualified;
- complaint telemetry is missing or reaches/exceeds 0.1%.

`DRY_RUN` and `INTERNAL_RECIPIENTS` are not blocked by these scaled-delivery gates.

## Operations

- Scheduler: refreshes deliverability evidence before Email automation/campaign/sequence processing and records the refresh summary in the scheduler audit.
- Manager API: `GET /api/email/deliverability` returns persisted evidence; `POST /api/email/deliverability` force-refreshes the current workspace.
- Production CLI: `scripts/email-deliverability-refresh.ts` force-refreshes and prints machine-readable evidence for deployment/certification.
- Scaled production preflight: requires explicit workspace and sender and reads the persisted evidence from the database. Manual SPF/DKIM/DMARC/rate env values cannot bypass the gate.

## Rollout boundary

P1 may be deployed in `DRY_RUN` with external writes disabled. Deploying P1 is not authorization for `LIMITED_COHORT` or `LIVE` and must not toggle either mode.
